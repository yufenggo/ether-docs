# 提案：平台底座（多租户后台管理平台）

## 背景与目标

建设一款**多租户后台管理平台底座**，作为统一基础，后续在其上**孵化业务系统**
（详见 [../../product/vision.md](../../product/vision.md)）。本提案是底座的**总立项**：
界定范围、能力分解与建设顺序；**各能力的详细设计在后续独立的 changes / specs 中落地**。

## 要解决什么

- 各业务系统重复造"租户 / 登录 / 鉴权 / 审计"等轮子 → 由底座**统一提供、业务复用**。
- ToB 合规对认证、权限、审计的基线要求 → 在平台层**一次性满足**，业务不再各自实现。

## 范围（底座包含的能力，按建设优先级）

1. **多租户基础**：租户模型、租户间隔离、租户管理。
2. **身份与访问**：登录、认证（authn）、授权（RBAC 角色-权限）。
3. **审计**：关键操作留痕，可查询 / 导出。
4. **合规基线**：密码与会话策略、数据保护等（随目标合规标准细化）。
5. **业务孵化扩展机制**：业务系统如何挂载到底座、复用其能力。

## 不做（out of scope）

- 具体业务功能本身（待业务规划）。
- 非 HTTP/JSON 通信形态（受 gale 边界：无 gRPC/WebSocket/SSE）。
- 计费 / 订阅、开放第三方 API、多端适配（如后续需要再单独立项）。

## 必须先定的地基决策（阻塞后续设计，将在 design 阶段调研后定）

1. **多租户隔离模型**：共享库行级（tenant_id）／按租户 schema／按租户独立库。
2. **RBAC 粒度**：角色-权限-资源；是否需要数据级权限 / ABAC。
3. **审计事件范围**：记录哪些、存哪里、留存多久、如何查导。
4. **目标合规标准**：等保 / ISO 27001 / SOC 2 等——决定基线要求。

## 验收标准（怎样算底座可用）

- 能创建 / 管理多个租户，**租户间数据隔离可验证**（A 租户读不到 B 租户数据）。
- 用户可登录；**认证 + RBAC 授权在接口层生效**（越权请求被拒）。
- 关键操作（登录、权限变更、租户管理等）产生**可查的审计日志**。
- 一个**示例业务系统**能复用底座能力跑通最小闭环（证明孵化机制有效）。
- 全程具备 OpenAPI 契约、测试与文档。
