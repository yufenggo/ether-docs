# ADR-0006：审计采用独立模块 + 事务内写入 + 分层落点 + 统一模板

> ADR = Architecture Decision Record（架构决策记录），记录本决策"为什么"。见 [ADR-0001](0001-record-architecture-decisions.md)。
> 名词：审计 = 面向合规、可追责、对外不可改的业务事件记录（≠ 排障应用日志）；
> 事务性发件箱（transactional outbox）= 与业务变更同事务先写待发事件、再由中继异步发布，避免"已提交但事件丢失"。

- **状态**：accepted
- **日期**：2026-06-20
- **关联**：承接 [ADR-0004](0004-multi-tenant-db-per-tenant.md)、[ADR-0005](0005-rbac-self-built-per-tenant.md)；
  对应 2026-06 平台底座（在途 changes/）决策 D3。

## 背景
平台需要面向合规的审计能力。在 db-per-tenant（每租户独立库、数据可驻留客户侧）下，需定：审计数据落点、
写入方式与一致性、防篡改强度、留存策略，以及审计能力如何对业务模块暴露。

## 决策
1. **独立审计模块**，对内部业务模块暴露两种接入，统一产出**统一模板**事件：
   - **编程 API / 钩子（主写入路径）**：业务在其**数据库事务内**调用 `audit.Record(ctx, event)`，
     审计记录与业务变更**同事务原子落库**（强一致、天然不丢）。
   - **gin 中间件自动采集**：对 HTTP 操作按路由自动生成事件。
2. **落点分层**：租户操作审计 → 该操作所在**租户库**；平台运营审计 → **控制平面中心库**。
3. **防篡改 / 写入边界**：审计对外 / 前端**只读**；写入与变更**只能由程序内部完成**（显式事务 / 归档定时任务），
   不暴露任何对外写改接口。一期不强制数据库物理 append-only（为后续归档留空间），哈希链待明确合规要求再加。
4. **留存**：当前**全量存储、不设留存期**；后续引入对象存储再划定归档 / 留存。
5. **传播（可选 / 二期）**：需跨库聚合 / 监控 / 归档时，用**事务性发件箱** + **JetStream 统一审计流**
   （按 `event_type` 区分），在事务内强一致写入之上叠加统一流。

## 取舍 / 备选方案
- **纯异步流（先入 JetStream 再落库）**：解耦、降延迟，但存在"业务已提交而事件投递失败"的丢失窗口；
  故改为"事务内写入为主、发件箱→流为传播补充"。
- **集中式审计（全部入中心库）**：查询聚合简单，但租户操作审计离开客户域，违背 D1/D2 数据主权；未选。
- **一期即上哈希链**：防篡改最强，但跨库 / 跨异步实现复杂、成本高，且与"后续定时归档"有张力；推迟到有明确合规要求。

## 影响
- 审计写入与业务操作**同事务**，对业务模块以钩子 / API 接入；新业务接入审计成本低。
- 形成"租户库审计 + 中心库平台审计"两处；全局聚合依赖（二期）传播流或按需查询。
- 审计事件类型清单与统一模板见 design.md D3，**类型清单可随业务演进增删**。
