# ADR-0004：多租户隔离采用 db-per-tenant（每租户独立库）

> ADR = Architecture Decision Record（架构决策记录），记录本决策"为什么"。见 [ADR-0001](0001-record-architecture-decisions.md)。

- **状态**：accepted
- **日期**：2026-06-20
- **关联**：限定（qualify）[ADR-0002](0002-backend-framework-gale.md)（gale 单 PostgreSQL）；
  对应变更：2026-06 平台底座（在途 changes/）的决策 D1。

## 背景
平台底座要支持多租户（一套系统服务多个互相隔离的租户）。隔离模型有三种经典谱系：
共享库行级（每表带 `tenant_id`）、按租户 schema、按租户独立库（db-per-tenant）。
同时存在一个强诉求：**业务数据可驻留在客户侧（data residency / 数据主权）**——
对等保 / 数据敏感的 ToB 客户，数据"不出客户域"是重要卖点。
约束方面，[ADR-0002](0002-backend-framework-gale.md) 规定后端基于 gale，其 gorm 封装为**单 PostgreSQL 单库**，
**不支持动态多数据源**（按租户切库）。

## 决策
1. **采用 db-per-tenant**：每个租户一个**独立数据库**，物理隔离。
2. **拓扑无关（topology-agnostic）**：租户连接以 **DSN（数据源连接目标）** 抽象，
   同一套应用代码**无痛兼容**三种部署形态、互不改码：
   ① 客户自托管库，应用跨网络远程连接；② 我们托管、每租户独立实例/库；
   ③ 同一实例下不同 database/schema。具体用哪种是**按租户的运维决策**，不进业务代码。
3. **平台自建租户数据源管理器**：因 gale 不支持动态多数据源，租户库连接**不走 gale 的 db 管理**，
   由平台自建多数据源 / 动态连接池（按租户惰性建池并缓存），但**接入 gale 框架生命周期**
   （配置经 viper、日志经 zap、随服务优雅启停关闭连接池）。
4. **控制平面 / 数据平面分层**：
   - 控制平面（用 gale 默认单库）：租户注册表、每租户连接配置（DSN，加密存储 + 密钥管理）、
     平台级超级管理员、平台级审计、安全策略基线。
   - 数据平面（每租户独立库）：该租户业务数据。
5. **不引入 PostgreSQL 行级安全（RLS）**：物理分库已天然隔离，无"忘加 `WHERE tenant_id`"的泄漏面。

## 取舍 / 备选方案
- **共享库行级 `tenant_id`**：租户密度最高、运维最简，但只是**逻辑隔离**、且**无法做到数据驻留客户侧**；
  不满足数据主权诉求，未选。
- **schema-per-tenant**：隔离与按租户迁移居中，但仍是同库内、同样无法数据驻留客户侧；未选。
- **db-per-tenant（选用）**：隔离最强、支持数据主权；代价是运维最重、租户密度最低，已接受。
- **gale 多数据源**：gale 不支持 → 选择"在 gale 门面之外自管租户连接、但接入其生命周期"，
  从而**限定而非推翻** ADR-0002（控制平面仍是 gale 单库）。

## 影响
- **架构**：形成"控制平面单库 + 数据平面多库"两层；请求需**先定位租户、再取其库连接**。
- **安全**：连接串加密存储 + 密钥管理；跨网络连库需 TLS / VPN / 专线。
- **迁移**：schema 变更要**逐租户库执行**，需处理客户库不可达 / 版本漂移（灰度、版本协商）。
- **可用性**：某租户库或链路故障 → **仅该租户不可用**（局部故障，模型固有）。
- **后续**：租户内用户与 RBAC 策略的落点（控制平面 vs 租户库）在 D2 决策中确定。
